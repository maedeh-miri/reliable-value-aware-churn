# Primary Model Configuration v1

**Status:** Frozen — Primary Model Configuration v1.

## 1. Purpose and Scope

This document records the primary model configuration selected
for the first version of the Reliable Value-Aware Churn Decisions
project.

The configuration is based on train-only, group-aware
cross-validation and predefined robustness and sensitivity analyses.

The purpose of this freeze is to establish a reproducible and
transparent model configuration before proceeding to probability
calibration and retention decision modeling.

The freeze covers:

- Predictor selection and feature governance.
- Feature preprocessing and encoding.
- Classification algorithm and hyperparameters.
- Model training and validation protocol.
- Evidence supporting the selected configuration.

The freeze does not yet cover:

- Probability calibration methods.
- Decision thresholds.
- Customer retention targeting policies.
- Budget and capacity constraints.
- Final held-out test evaluation.

Selecting this configuration does not establish that Logistic
Regression is the best possible model.

It represents a documented and defensible baseline for the
subsequent stages of this project.

## 2. Selected Model and Prediction Task

### 2.1. Prediction Task

The project uses the UCI Iranian Churn Dataset.

According to the dataset documentation, the predictor variables
represent information aggregated over the first nine months,
while the churn label describes customer status at the end
of month twelve.

The intended prediction point is therefore the end of month nine,
with a three-month planning horizon.

The binary target is defined as:

- Churn = 1: Customer churn.
- Churn = 0: No customer churn.

Dataset reference:
https://doi.org/10.24432/C5JW3Z

### 2.2. Selected Model

The selected primary model for version 1 is Logistic Regression,
implemented using scikit-learn.

The classifier and its preprocessing transformations are combined
inside a single Pipeline.

The model estimates the probability associated with the positive
class (Churn = 1).

The positive-class probability is obtained using:

`predict_proba(X)[:, 1]`

At this stage, these outputs are not claimed to be calibrated.

Probability calibration will be addressed separately after the
primary model configuration has been validated and frozen.

### 2.3. Model Role

The predictive model estimates customer churn risk.

It does not directly estimate:

- The causal effect of a retention intervention.
- The probability that a customer responds to an intervention.
- The financial profit generated by retaining a customer.

Retention decisions will be addressed in a separate decision
modeling stage.

The primary classifier will be fitted using the frozen Train split.

The Calibration split is reserved for the predefined calibration
stage, and the Test split remains untouched until final evaluation.

## 3. Feature and Preprocessing Configuration

### 3.1. Selected Predictors

The primary model uses exactly ten predictors.

Original CSV column names are preserved, including repeated
spaces in certain column names.

| Predictor | Feature Type | Preprocessing |
|---|---|---|
| `Call  Failure` | Numeric | StandardScaler |
| `Subscription  Length` | Numeric | StandardScaler |
| `Charge  Amount` | Numeric | StandardScaler |
| `Seconds of Use` | Numeric | StandardScaler |
| `Frequency of use` | Numeric | StandardScaler |
| `Frequency of SMS` | Numeric | StandardScaler |
| `Distinct Called Numbers` | Numeric | StandardScaler |
| `Complains` | Binary | Passthrough |
| `Age Group` | Categorical | OneHotEncoder |
| `Tariff Plan` | Categorical | OneHotEncoder |

### 3.2. Preprocessing Strategy

Preprocessing is implemented using scikit-learn's
ColumnTransformer.

The seven numeric predictors are standardized using
StandardScaler.

Treating Charge Amount as numeric is a modeling choice
supported by the train-only sensitivity analysis.
It does not establish that the variable represents a
truly continuous monetary quantity.

The binary Complains predictor is passed through without
additional transformation.

Age Group and Tariff Plan are encoded using OneHotEncoder
with the following configuration:

`handle_unknown="ignore"`

All preprocessing transformations are contained within
the model Pipeline.

During cross-validation, preprocessing parameters are
learned only from the fitting portion of each fold.

For the subsequent calibration stage, the primary model
and its preprocessing will be fitted using the frozen
Train split only.

### 3.3. Excluded Predictors

The following variables are excluded from the primary
prediction model:

- Status: Excluded conservatively because its semantic
  meaning and temporal availability are insufficiently
  established. Data leakage has not been proven.

- Customer Value: Reserved for the subsequent retention
  decision layer rather than used as a model predictor.

- Age: Excluded because the dataset audit established an
  exact deterministic correspondence with Age Group.

The target variable Churn is never used as a predictor.

These decisions follow the documented feature governance
and train-only robustness analyses.

## 4. Model Hyperparameters

### 4.1. Classifier Configuration

The primary classifier is implemented using:

`sklearn.linear_model.LogisticRegression`

The explicitly configured hyperparameters are:

| Hyperparameter | Value |
|---|---|
| C | 1.0 |
| solver | lbfgs |
| max_iter | 1000 |

The corresponding classifier construction is:

`LogisticRegression(C=1.0, solver="lbfgs", max_iter=1000)`

Parameters not explicitly specified in the implementation
follow the defaults of the pinned scikit-learn version.

The reference environment uses scikit-learn 1.9.1.

### 4.2. Regularization

The C parameter controls the inverse of regularization
strength.

Smaller C values correspond to stronger regularization.

The effective default regularization configuration in the
reference scikit-learn version is L2.

The initial value C=1.0 is retained following the
train-only regularization sensitivity analysis.

Although C=10.0 produced slightly better mean
cross-validation metrics, the observed improvements were
small and did not establish a meaningful practical or
statistical advantage.

Therefore, the available evidence does not provide
sufficient justification to replace the initial
configuration.

### 4.3. Optimization

The lbfgs solver is used to optimize the Logistic
Regression objective.

The maximum iteration limit is set to 1000.

This value specifies an upper bound on optimization
iterations, not a requirement to perform exactly
1000 iterations.

The previously recorded cross-validation runs
reported approximately 33 to 36 optimization iterations.

### 4.4. Configuration Reproducibility

The reference implementation is defined in:

`experiments/logistic_baseline_cv.py`

The classifier is constructed by:

`build_logistic_pipeline()`

The preprocessing and classifier are contained within
a single scikit-learn Pipeline.

No hyperparameter selection is permitted using the
reserved Calibration or Test splits.

Further changes to the primary configuration would
require an explicitly documented revision supported
by an appropriate train-only evaluation protocol.

Reference:
https://scikit-learn.org/stable/modules/generated/sklearn.linear_model.LogisticRegression.html

## 5. Train-only Cross-Validation Evidence

### 5.1. Evaluation Protocol

Model development and evaluation were conducted using
the frozen Train split only.

The Train split contains:

- Total observations: 1894
- Positive observations (Churn = 1): 299
- Positive-class prevalence: approximately 15.79%

Internal cross-validation uses:

`StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=42)`

Groups are defined using exact equality across the ten
approved prediction features.

A fresh preprocessing and classification Pipeline is
fitted within each cross-validation fold.

Group isolation between the fitting and validation
portions is checked.

The reserved Calibration and Test splits are not used
for model selection or hyperparameter tuning.

### 5.2. Baseline Comparison

The following values are previously recorded mean
cross-validation metrics.

| Metric | DummyClassifier | Logistic Regression |
|---|---:|---:|
| Accuracy | 0.8422 | 0.8986 |
| Precision | 0.0000 | 0.8432 |
| Recall | 0.0000 | 0.4414 |
| ROC-AUC | 0.5000 | 0.9288 |
| Average Precision | 0.1578 | 0.7589 |
| Brier Score | 0.1329 | 0.0715 |
| Log Loss | 0.4361 | 0.2294 |

The DummyClassifier uses the prior-class strategy.

Its relatively high accuracy reflects the class
imbalance and does not indicate useful discrimination.

Logistic Regression achieves substantially better
train-only cross-validation performance across the
reported discrimination and probabilistic metrics.

### 5.3. Cross-Validation Variability

The previously recorded standard deviations across
the five Logistic Regression folds are:

| Metric | Mean | Standard Deviation |
|---|---:|---:|
| ROC-AUC | 0.9288 | 0.0056 |
| Average Precision | 0.7589 | 0.0207 |
| Brier Score | 0.0715 | 0.0027 |
| Log Loss | 0.2294 | 0.0058 |

These standard deviations describe variability
across the recorded cross-validation folds.

They should not be interpreted as confidence
intervals for generalization performance.

### 5.4. Scientific Interpretation

The results support Logistic Regression as a
reasonable primary model for the next project stage.

However:

- These are development-stage cross-validation results.
- They are not final held-out test results.
- Strong ROC-AUC does not establish probability calibration.
- Brier Score and Log Loss reflect more than calibration alone.
- Precision and Recall use the default classification threshold.
- The default threshold is not the final retention policy.
- Cross-validation results do not establish causal effects.
- No claim of statistical superiority over all alternative
  models is made.

Independent probability calibration and final held-out
evaluation remain separate project stages.

Reference:
https://scikit-learn.org/stable/modules/model_evaluation.html

## 6. Robustness Evidence and Selection Rationale

### 6.1. Scope of Sensitivity Analyses

Four train-only robustness and sensitivity analyses
were conducted before freezing the primary model
configuration.

The analyses examined:

- Removing the Complains predictor.
- Numeric versus One-Hot encoding of Charge Amount.
- One-Hot versus ordinal encoding of Age Group.
- Alternative Logistic Regression regularization strengths.

These analyses assess sensitivity to the examined
modeling choices.

They do not establish global model optimality or
causal relationships.

### 6.2. Complains Ablation

Removing Complains reduced predictive performance.

The mean changes for the model without Complains,
relative to the full model evaluated on matching folds,
were:

| Metric | Mean Change |
|---|---:|
| ROC-AUC | -0.0476 |
| Average Precision | -0.1881 |
| Brier Score | +0.0216 |
| Log Loss | +0.0579 |

For this experiment, the internal Train groups were
reconstructed using the nine remaining predictors.

Both compared models were evaluated using the same
folds derived from these nine-feature groups.

Consequently, these results should not be compared
directly with the original ten-feature CV results
as if the fold assignments were identical.

Decision: Retain Complains.

Its predictive contribution does not establish
a causal effect on customer churn.

### 6.3. Charge Amount Encoding

Numeric scaling was compared with One-Hot encoding.

The mean changes for One-Hot relative to Numeric were:

| Metric | Mean Change |
|---|---:|
| ROC-AUC | -0.0023 |
| Average Precision | -0.0017 |
| Brier Score | +0.0003 |
| Log Loss | +0.0024 |

The observed differences were small.

Decision: Retain numeric scaling.

This does not establish that Charge Amount is
a truly continuous or monetary variable.

The previously identified value 10 observations
were retained without automatic modification.

### 6.4. Age Group Encoding

One-Hot encoding was compared with ordinal numeric
encoding followed by scaling.

The mean changes for ordinal encoding relative
to One-Hot were:

| Metric | Mean Change |
|---|---:|
| ROC-AUC | -0.0049 |
| Average Precision | -0.0112 |
| Brier Score | +0.0014 |
| Log Loss | +0.0051 |

One-Hot encoding performed slightly better
across the reported mean metrics.

Decision: Retain One-Hot encoding.

This choice also avoids imposing equal numerical
distances between the age-group categories.

### 6.5. Regularization Sensitivity

Three predefined values were evaluated:

- C = 0.1
- C = 1.0
- C = 10.0

The train-only cross-validation results were:

| C | ROC-AUC | AP | Brier | Log Loss |
|---|---:|---:|---:|---:|
| 0.1 | 0.9232 | 0.7361 | 0.0763 | 0.2473 |
| 1.0 | 0.9288 | 0.7589 | 0.0715 | 0.2294 |
| 10.0 | 0.9294 | 0.7622 | 0.0711 | 0.2283 |

C=10.0 produced slightly better mean results
than C=1.0.

However, the observed improvements were small,
and no statistically or practically meaningful
advantage was established.

Decision: Retain the initial C=1.0 configuration.

This decision does not establish that C=1.0
is globally optimal.

### 6.6. Selected Configuration for Version 1

Based on the recorded train-only evidence,
the primary model configuration retains:

- Logistic Regression.
- The ten approved prediction features.
- Complains as a binary predictor.
- Numeric scaling for Charge Amount.
- One-Hot encoding for Age Group.
- One-Hot encoding for Tariff Plan.
- C=1.0.
- solver="lbfgs".
- max_iter=1000.

The selected configuration provides a documented
and reproducible starting point for probability
calibration.

These choices were made using development-stage
Train evidence without using the reserved Test split.

The Calibration split has not been used to choose
the primary model configuration.

Supporting documentation:

- docs/complains_ablation.md
- docs/charge_encoding_sensitivity.md
- docs/age_encoding_sensitivity.md
- docs/regularization_sensitivity.md

## 7. Data Boundaries and Leakage Prevention

### 7.1. Frozen Data Split

The project uses the previously frozen version 1
group-aware data split.

| Split | Observations | Churn = 1 | Churn Rate |
|---|---:|---:|---:|
| Train | 1894 | 299 | 15.79% |
| Calibration | 628 | 98 | 15.61% |
| Test | 628 | 98 | 15.61% |

The split is recorded in:

- data/splits/v1_manifest.csv
- data/splits/v1_metadata.json

The split was constructed using StratifiedGroupKFold
with groups defined by exact equality across the
ten approved prediction features.

Group isolation across the frozen splits was validated.

The frozen split must not be regenerated or modified
during subsequent model development.

### 7.2. Train Split

The Train split is used for:

- Model development.
- Group-aware cross-validation.
- Predictor and preprocessing sensitivity analyses.
- Hyperparameter sensitivity analyses.
- Fitting the selected primary model.

Preprocessing is fitted only on the relevant training
portion within each cross-validation fold.

For the subsequent calibration workflow, the selected
primary model will be fitted on the frozen Train split.

### 7.3. Calibration Split

The Calibration split is reserved for the predefined
probability calibration procedure.

The calibration method and evaluation protocol must
be documented before fitting the calibrator.

The Calibration split must not be reused indiscriminately
for repeated model or hyperparameter selection.

If multiple calibration methods are to be compared,
a leakage-aware selection procedure must be designed
without using the reserved Test split.

Performance measured on the same observations used
to fit a calibrator is not an independent estimate
of its generalization performance.

The detailed calibration protocol will be documented
separately.

### 7.4. Test Split

The Test split is reserved for final held-out
evaluation after the relevant development decisions
have been finalized.

It must not be used to select or revise:

- Prediction features.
- Preprocessing transformations.
- Model hyperparameters.
- Calibration methods.
- Classification thresholds.
- Retention targeting policies.
- Budget-dependent decision rules.

The split construction and integrity checks used
target information to establish and validate the
frozen assignments.

However, the Test split has not been used for
predictive model evaluation or development-stage
configuration selection.

Final Test results must not be used to retroactively
tune the evaluated configuration.

### 7.5. Limitations of Group-Aware Splitting

The frozen split prevents exact predictor-defined
groups from appearing across different splits.

However, it is not:

- A chronological split.
- A split based on verified customer identities.
- A guarantee against all possible data leakage.
- A guarantee of future deployment performance.

The dataset does not provide a verified customer
identifier suitable for customer-level grouping.

These limitations must remain explicit in the
final scientific reporting.

References:

https://scikit-learn.org/stable/common_pitfalls.html

https://scikit-learn.org/stable/modules/calibration.html

## 8. Freeze Status and Next Steps

### 8.1. Primary Model Configuration v1

The proposed primary model configuration for version 1
is Logistic Regression with the ten approved predictors
and the preprocessing and hyperparameters documented
in this file.

This configuration was selected using train-only
development evidence.

The purpose of the freeze is to establish a stable,
reproducible baseline before probability calibration.

The configuration must pass final documentation and
implementation checks before its status is changed
from Draft to Frozen.

### 8.2. Freeze Validation Requirements

Before declaring the configuration frozen, the
following conditions must be verified:

- The documented predictors match the implementation.
- The preprocessing configuration matches the implementation.
- The classifier hyperparameters match the implementation.
- The frozen split validation succeeds.
- The relevant automated tests pass.
- The documented evaluation results are internally consistent.
- The repository changes are reviewed.
- No unintended changes to data or split artifacts occurred.

Successful validation will allow the configuration
to be formally marked as Frozen.

### 8.3. Subsequent Probability Calibration

After the model configuration is frozen, the project
will proceed to probability calibration.

The next stage will include:

- Defining a calibration protocol before fitting.
- Reviewing calibration methods and their assumptions.
- Preserving separation between model training
  and calibrator fitting data.
- Implementing a reproducible calibration workflow.
- Evaluating and documenting calibration limitations.
- Maintaining the reserved Test boundary.

The calibration method is not selected by this
model configuration document.

Calibration decisions will be documented separately
under an appropriate leakage-aware protocol.

### 8.4. Change Control

The frozen version 1 configuration should not be
modified silently.

Any subsequent material change must:

- Have an explicit methodological justification.
- Be supported by an appropriate evaluation protocol.
- Avoid using the Test split for development decisions.
- Be documented as a configuration revision.
- Preserve the reproducibility of the original version.

The final held-out evaluation remains a separate
stage after the relevant development decisions
have been finalized.
